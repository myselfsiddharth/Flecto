# Training the secret classifier

Not published. `package.json`'s `files` field ships `index.js`, `src/**/*`,
`schemas/**/*`, and the top-level docs; this directory is not among them. What
reaches a user is `src/classifier-weights.json` and the inference code that
reads it.

```bash
node training/train.js --dry-run   # train and evaluate, write nothing
node training/train.js             # rewrite src/classifier-weights.json
npm run bench:classifier           # the published confusion matrix
```

Training takes about 30 seconds.

## Provenance of every training example

There is no corpus to train on, and **we cannot collect one**. User
configuration files are the last thing this project should be gathering — Flecto
reads `.env` files, SOPS documents, and Terraform plans, and [#113] was a
sensitive-value leak. So every example is synthesized or hand-written, and
`corpus.js` is the provenance record: if a class of value is in the model, it is
visible in that file, in source, in a diff.

Nothing here was scraped, downloaded, or copied from a real repository. There is
no third-party data and therefore no third-party licence to carry.

### Positives — synthesized key material

Generated by `generateSecrets()` from a seeded PRNG over three alphabets:

| Encoding | Why |
|---|---|
| standard base64 (with `+` and `/`) | the gap the charset gate cannot see **by construction** |
| base64url (with `-` and `_`) | the common token encoding |
| base62 | vendor tokens without padding characters |

Lengths 20–64, weighted toward the short end because that is where the entropy
gate's recall is worst. Padding (`=`, `==`) is applied about 30% of the time, as
real base64 is.

They deliberately carry **no vendor prefix**. Anything with a known prefix is
caught by the format detectors, never reaches the classifier, and training on it
would only teach the model to recognize something it is never shown.

**Hex and base32 are deliberately excluded**, although [#136] lists them. A
40-character lowercase-hex secret and a git SHA are the same alphabet, length,
and entropy; an uppercase base32 secret and a TOTP seed likewise. They are not
hard to separate — they are *undecidable from the value alone*, and [#136]'s own
negatives list names git SHAs. Recall bought there would be paid for out of the
zero-false-positive floor, which is the one thing the issue says not to trade.

### Negatives — synthesized benign configuration

Generated by `generateBenign()` as **families**, not literals, so the model is
pushed on the whole shape rather than memorizing a few strings. The three
residual false-positive classes named in `secrets.js`'s own header are families
here: `CustomerSuccessDashboard2026`, `AcmeVpnGateway01Prod`,
`PRODUCTION_us_east_1_Config2024`.

Also covered: UUIDs, subresource-integrity digests, git SHAs, container image
refs (tag and digest forms), ARNs, ISO-8601 timestamps, hostnames, URLs,
connection strings without credentials, filesystem paths, semver and ranges,
kebab/snake/camel identifiers, base64 of ordinary text, templated `${VARS}`,
Kubernetes resource names, cron expressions, and opaque *public* identifiers
such as Google Place IDs.

The last group was added after scoring the holdout and reading what came out on
top — which is the only honest way to choose hard negatives.

### Held-out evaluation

Never trained on:

- `benignHoldout()` — hand-written values a reviewer would name if asked "what
  would embarrass us". A model that gets these right by memorization proves
  nothing, so they are excluded from training entirely.
- `secretHoldout()` — generated from a **different seed**, weighted toward
  `/`-bearing standard base64.

Both are filtered to the classifier's operating band (≥ 24 characters) before
evaluation, because that is the population it is actually asked about.

## Reproducibility

The weights are only an auditable artifact if they can be regenerated:

- The corpus comes from a seeded xorshift128, not `Math.random`, which cannot be
  seeded.
- Ordering is fixed everywhere, including the n-gram vocabulary, which sorts by
  count **then lexically** so ties cannot reorder between runs.
- Optimization is plain batch gradient descent with a fixed iteration count. No
  shuffling, no dropout, no early stopping on a random split.
- Weights are rounded to 6 decimals, so the file is a readable diff and is
  identical across platforms whose last-bit float formatting might differ.

`test/classify.test.js` asserts the corpus regenerates identically and that the
shipped weights match the features the build computes.

## The ship criterion

`train.js` **refuses to write weights** that produce a false positive on the
benign holdout, and `bench/classifier.js` exits non-zero if the classifier adds
one. From [#136]:

> If it cannot clear the first bullet, close this issue and keep the heuristic.

That remains the standard. If a future change to the corpus or the features
cannot hold zero added false positives, the right answer is not to lower the
bar.

## Changing the model

Changing the weights changes which values get masked, so it is a **breaking
change**, handled with the same semver care as changing a policy pack default:

1. Edit `corpus.js` or `classifier-features.js`.
2. `node training/train.js --dry-run` and read the numbers.
3. `node training/train.js`, then `npm run bench:classifier`.
4. Bump `modelVersion` in `train.js` (it travels in the envelope as
   `classifier_version`).
5. Update the published numbers in [`docs/secret-classifier.md`](../docs/secret-classifier.md).

Adding a shape feature anywhere but the **end** of `SHAPE_FEATURES` invalidates
existing weights; `classify.js` checks the names at load and throws rather than
scoring nonsense.
